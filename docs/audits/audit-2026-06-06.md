## 🔴 CRITICAL findings (6) — fix before next deploy

### 1. `resetAll` hard-deletes org-wide production data when called by a non-demo admin

[src/features/admin/actions.ts:39](src/features/admin/actions.ts#L39) — _data-integrity_

```ts
await tx.leaveRequest.deleteMany({ where: sessionWhere });
await tx.leaveBalance.deleteMany({ where: sessionWhere });
// ... hard-deletes Person, Team, Department, LeaveType ...
```

`getDemoSessionId()` returns `null` for any non-demo caller. The `where: { sessionId: null }` clause then hard-deletes every row where `sessionId IS NULL` — i.e. **all org-wide production rows**. The audit payload captures only aggregate row counts, so reconstruction is impossible.

**Fix:** refuse to run unless `sessionId` is non-null (demo-only), OR capture row contents in the audit `before` payload before deleting, OR move to soft-delete here too.

### 2. 2FA verification can be bypassed by a stale JWT against a disabled-but-required user

[src/features/twoFactor/actions.ts:259](src/features/twoFactor/actions.ts#L259) — _error-paths_

```ts
if (!tfa?.enabled) {
  // 2FA not enabled — nothing to verify
  return; // ⚠️ silently returns ActionResult success
}
```

Chain: JWT cached with `twoFactorRequired=true` → admin runs `adminResetTwoFactor` (line 320) deleting the TFA row → user lands on `/auth/verify-2fa` → `verifyTwoFactorLogin` returns success without verifying any code → client calls `update({ twoFactorVerified: true })` → user gets `twoFactorVerified=true` without proving possession of the authenticator. **Auth bypass.**

**Fix:** `throw new ActionError("twoFactorNotEnabled", ...)` when `tfa?.enabled === false`. Also clear `twoFactorRequired` from the JWT inside the auth callback whenever the DB row is missing.

### 3. AUDIT_HMAC_SECRET silently falls back to a hardcoded dev secret in source

[src/lib/auditHashChain.ts:9](src/lib/auditHashChain.ts#L9) — _external-boundaries_ + _error-paths_

```ts
return process.env.AUDIT_HMAC_SECRET ?? "dev-audit-hmac-secret-change-in-production";
```

Any production deployment that forgets to set the env var emits and _verifies_ audit logs with a key the whole world knows (it's in the public source). The `/api/audit/verify` endpoint returns `valid: true` on forged entries; the chain becomes security theatre. README.md:401 makes this worse by claiming the variable is "auto-generated if missing" — the code does no such thing.

**Fix:** throw at startup when `NODE_ENV === "production" && !AUDIT_HMAC_SECRET`. Add a `/api/ready` check that reports `status: 'error'` if the env var is missing. Never ship a baked-in fallback for an HMAC secret.

### 4. 2FA enforcement exempts every `/api/*` route

[src/proxy.ts:60](src/proxy.ts#L60) — _external-boundaries_ + _error-paths_

```ts
if (
  !pathname.startsWith("/api") &&
  !pathname.startsWith("/auth") &&
  !pathname.startsWith("/_next")
) {
  // ...check twoFactorVerified...
}
```

`/api/calendar` (returns approved leave for any person in the org), `/api/audit/verify`, `/api/realtime/sse`, `/api/realtime/poll` all run without checking `session.user.twoFactorVerified`. A user with `twoFactorRequired=true` and `twoFactorVerified=false` can exfiltrate the iCal feed and the realtime event stream **with 2FA bypassed**.

**Fix:** remove the `/api` carve-out from the gate, OR add an explicit `twoFactorVerified` check inside each `/api/*` handler that accesses tenant data. Only `/api/health` and `/api/ready` need exemption.

### 5. Audit-export background worker doesn't scope by `sessionId` — cross-tenant audit log exfiltration

[src/jobs/workers/auditExport.ts:40](src/jobs/workers/auditExport.ts#L40) — _external-boundaries_

```ts
const col = getAuditLogCollection();
const docs = await col.find(query).sort({ createdAt: -1 }).limit(10000).toArray();
//                       ^ query starts as {}, never adds sessionId
```

Every other audit-log read path enforces `sessionId` scoping (audit/queries.ts:27-29, 85-89). Every write tags `sessionId` (auditLog.ts:48,80,153,182). This worker doesn't. A demo user (or any user with `admin:manage_jobs` in one tenant) can enqueue a job that exports every audit log in the entire MongoDB collection, across all tenants/sessions.

**Fix:** pass `sessionId` (and userId for authorization) in the job payload, validate them, and add `query.sessionId = sessionId` (plus permission check) before running `find`.

### 6. Demo Credentials provider enabled by default; one-click superuser in any production deployment that forgets `NEXT_PUBLIC_DEMO_LOGIN=false`

[src/auth.ts:41](src/auth.ts#L41) — _external-boundaries_

```ts
Credentials({
  id: "demo",
  authorize() {
    let user = await prisma.user.findUnique({ where: { email: DEMO_EMAIL } });
    if (!user) {
      user = await prisma.user.create({
        data: { email: DEMO_EMAIL, name: "Demo User", role: "superuser" },
      });
    }
    // ...
  },
});
```

The provider is gated by `process.env.NEXT_PUBLIC_DEMO_LOGIN !== "false"` — fail-OPEN. Any deployment that doesn't set the flag exactly to the string `"false"` (typo, empty, unset) ships an unauthenticated "click here to log in as superuser" button. The first invocation in production creates `DEMO_EMAIL` as `role: "superuser"`, bypassing the OAuth-only first-user logic.

**Fix:** invert the default. Require `NEXT_PUBLIC_DEMO_LOGIN === "true"` to enable. Additionally refuse the demo provider in `NODE_ENV === "production"` unless an extra opt-in is set.

## 🟠 HIGH-severity findings (25)

### Resource lifecycle (3)

- **[src/auth.ts:143](src/auth.ts#L143)** — Session create + active-session enforcement runs as 3 sequential Prisma calls outside any transaction; concurrent sign-ins can quietly exceed `MAX_CONCURRENT_SESSIONS`. - **[src/jobs/queue.ts:19](src/jobs/queue.ts#L19)** — Every cold-start Lambda touching a job action constructs a fresh PgBoss with its own pg pool + 30s monitor interval. No SIGTERM/SIGINT handler calls `stopJobQueue()`. Pool exhaustion risk under bursty admin traffic.
- **[src/jobs/workers/index.ts:10](src/jobs/workers/index.ts#L10)** — `registerAllWorkers` is exported but **never called at runtime** (only in tests). Jobs are enqueued by the admin UI but no worker processes them. `cleanupExpiredRateLimits` and audit-export jobs never run. The `pgboss.job` table grows unbounded.

### Data integrity (8)

- **[src/auditLog.ts:109](src/auditLog.ts#L109)** — Cross-DB consistency: PG mutation commits, audit-log MongoDB `insertMany` runs in `after()`. If Mongo fails, the catch only logs — no Sentry, no retry, no outbox row. Mutations succeed without an audit trail.

Two concurrent server actions in the same session can both read the same `prevHash` and both insert — the chain forks into a DAG. The losing branch can be deleted with no detectable gap.
- **[src/features/leave/actions.ts:215](src/features/leave/actions.ts#L215)** — Year boundary bug: a Dec 28–Jan 4 leave request uses `startDate.getFullYear()` for balance lookup. All 8 days deduct from the start-year balance even though only 4 fall in that year.

Pre-flight check at line 219 happens at creation, not approval. Parallel approvals can push `used > allocated`; no DB CHECK constraint prevents negative remaining.

## Cross-cutting patterns

1. **`captureServerActionError` is dead code everywhere.** Multiple audits agree: defined in `src/lib/sentryCapture.ts`, used only by `global-error.tsx`. Server actions throw, errors are swallowed by `safe()`, Sentry never sees them. **This is the single biggest observability gap.**

2. **CLAUDE.md says all mutations go through `$transaction`. Several auth/session/cleanup paths violate this:** `src/rateLimit.ts:89`, `src/auth.ts:143`, the demo `authorize()` flow, the audit log `after()` writer. Worth a pass to bring these into compliance.

3. **Cross-DB consistency between Postgres and MongoDB is best-effort.** Every mutation commits to PG → audit-log write happens later via `after()` → if Mongo is unavailable, the audit is lost with only a `logger.error`. For a system that pitches a hash-chained audit log as forensic-grade, this is the biggest integrity story missing.

4. **2FA correctness is multi-system fragile.** `twoFactorRequired` is set on the JWT only during full refresh, `twoFactorVerified` is trusted from client `useSession().update(...)`, `/api/*` is exempt from the gate, and `verifyTwoFactorLogin` silent-success-when-disabled creates a bypass. At least 4 of the 6 critical findings are 2FA-adjacent.

5. **Demo mode and production share too much surface.** Default-on demo provider creates a real superuser row; `getDemoSessionId()` returning null in production turns session-scoped queries into org-wide queries (the `resetAll` critical). A clearer compile-time separation would prevent half these findings.
