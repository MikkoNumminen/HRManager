## Findings

### defensive-impossible (8 confirmed)

Redundant null-checks / fallbacks on values whose type already proves they're non-nullable. Pattern is concentrated in report queries — likely originated as a single copy-paste template that was repeated across four report types.

#### [src/features/dashboard/queries.ts:153](src/features/dashboard/queries.ts#L153) — `t.memberCount ?? 0` after Zod parse — medium

`validatedTeamSizes.map((t) => ({ memberCount: t.memberCount ?? 0 }))`. `TeamSizeRowSchema` (line 20) declares `memberCount: z.number().int().nonnegative()` — required, non-nullable. After `.parse()` on line 139, `t.memberCount` is statically typed `number`. `?? 0` is dead code.

#### [src/features/dashboard/queries.ts:157](src/features/dashboard/queries.ts#L157) — `d.teamCount ?? 0` after Zod parse — medium

Same pattern with `DepartmentSizeRowSchema` (line 25). Sibling pattern on line 147 (`counts?.totalPersons ?? 0`) IS legitimate because `counts` can be undefined from `array[0]`, but the iterated `.map` callbacks on validated arrays are not.

#### [src/features/dashboard/queries.ts:160-163](src/features/dashboard/queries.ts#L160-L163) — 4 redundant fallbacks on `growthTimeline` — medium

`GrowthTimelineRowSchema` declares all four fields (`date`, `persons`, `teams`, `departments`) as required non-nullable. `?? "" / ?? 0` on lines 160-163 are all dead code. The explicit comment on line 137 (`"Validate raw SQL results with Zod before use"`) confirms validation has already happened.

#### [src/features/reports/queries.ts:144-146](src/features/reports/queries.ts#L144-L146) — `r.hired ?? 0`, `r.departed ?? 0`, `r.runningHeadcount ?? 0` after typed query — medium

The `HeadcountTrendRow` interface declares all three as required `number`. The SQL also `COALESCE`s them server-side and casts `::int`. The `?? 0` fallbacks actually **weaken safety**: if the DB ever returned null due to a bug, the fallback silently substitutes 0 and Zod never sees the violation. **Same pattern repeats** in three other functions in the same file: turnover (lines 246-254), leave utilization (309-319), review completion (362-370).

#### [src/features/employee/queries.ts:28](src/features/employee/queries.ts#L28) — `return person ?? null` — low

`prisma.person.findFirst` already returns `{id, name} | null`. `(T | null) ?? null` is a no-op. The other four sibling functions in the same file use `if (!person) return null` then return the value directly — `getLinkedPerson` is the lone outlier.

#### [src/features/dashboard/queries.ts:230](src/features/dashboard/queries.ts#L230) — `dept.headId ?? null` on `String?` Prisma field — low

`Department.headId` is `String?` so the Prisma client already types it `string | null`. `(string | null) ?? null` is a no-op. Same pattern on lines 235, 240, 241, 248, 253, 254, 262, 263.

> **Adversarial verifier caught nuance:** the pattern `dept.head?.name ?? null` (lines 231, 236, 249) is **NOT** a redundant guard — the optional chain on a nullable relation yields `string | undefined`, and Zod `.nullable()` rejects `undefined`. The `?? null` there is load-bearing. Only the **scalar-on-model** lines are smells; **relation?.field** lines must stay. Verifier flagged this to prevent over-fix.

#### [src/features/reviews/queries.ts:224, 226](src/features/reviews/queries.ts#L224) — `subjectId ?? null`, `reviewerId ?? null` — low

`ReviewRequest.subjectId/reviewerId` are `String?` → already `string | null`. Lines 225/227 (`subject?.name ?? null`, `reviewer?.name ?? null`) are NOT smells — same nuance as above.

#### [src/features/persons/actions.ts:314](src/features/persons/actions.ts#L314) — `teamBefore?.teamManagerId` after null-throw — medium

Line 303 throws `ActionError` if `teamBefore` is falsy. TypeScript narrows `teamBefore` to non-null for the rest of the loop. Optional chain on line 314 protects against a case the guard above already eliminated. Cosmetic noise.

### swallowed-errors (8 confirmed)

#### [src/features/twoFactor/actions.ts:93](src/features/twoFactor/actions.ts#L93) — silent JSON.parse on 2FA recovery codes — **HIGH**

```ts
try {
  recoveryCodes = JSON.parse(recoveryCodesJson) as string[];
} catch {
  /* Ignore parse errors — codes were already shown to user */
}
```

The comment is misleading: the codes are shown in the UI, but the **hashed copies that the DB needs for `findMatchingRecoveryCode` (line 273) are never persisted**. On JSON.parse failure: empty `recoveryCodes` → empty `hashedCodes` (line 99) → DB write with `recoveryCodes: []` (line 110, 116) → 2FA enabled with **zero recovery codes** and `t("enabled")` success toast. No logger, no thrown ActionError, no user signal. `adminResetTwoFactor` provides an escape hatch (line 300), but the silent-on-write-failure behavior on a security-critical path is the real bug.

#### [src/auth.ts:188](src/auth.ts#L188) — silent `.catch(() => {})` on session lastActiveAt update — medium

This is **the only fully-empty `.catch(() => {})` in the entire src/ tree** (verifier confirmed via grep). Same file at line 62-64 handles an analogous "non-critical background" failure with `console.error("[demoSession] cleanupStaleDemoSessions failed:", err)` — so this is an outlier, not a convention. Downstream consequences: `lastActiveAt` drives admin "active sessions" sort order, concurrent-session eviction ordering, and stale-session cleanup. Silent failure means operators have zero signal when force-logout or concurrent-limit logic picks the wrong session to evict.

#### [src/features/twoFactor/components/TwoFactorSetup.tsx:51](src/features/twoFactor/components/TwoFactorSetup.tsx#L51) — client-side catch shows snackbar but no logging — low

Project has `src/lib/sentryCapture.ts` exporting `captureServerActionError(error, context)` precisely for this. **It's unused anywhere in the codebase except `global-error.tsx`** — direct evidence of an oversight rather than intentional design. Try/catch suppresses Sentry's auto-capture; failures on 2FA enrollment are invisible to monitoring.

#### [src/mongoDb.ts:103](src/mongoDb.ts#L103) — bare `catch {` on audit-log schema validator setup — medium

```ts
} catch { logger.warn("Could not apply schema validation to auditLogs collection"); }
```

The parameterless catch discards the error object at the language level — operator sees "Could not apply schema validation" with no triage info (permission denied? collection conflict? network?). Pino supports `logger.warn({ err: error }, ...)` for structured context; trivial fix. Same pattern at line 95 (outer catch). Audit-log schema validation is a security invariant; silent fallback to an unvalidated collection is dangerous.

#### [src/hooks/useRealtimeEvents.ts:73 + :82](src/hooks/useRealtimeEvents.ts#L73) — SSE event JSON.parse silently discarded — low

Two empty catches on `JSON.parse(e.data)` for SSE `mutation` and `notification` events. Also: the `as RealtimeEvent` is a cast — `RealtimeEventSchema` exists in `src/features/realtime/schemas.ts` but isn't used at runtime. A serialization regression would silently stop UI updates with zero signal.

#### [src/hooks/useRealtimeEvents.ts:128](src/hooks/useRealtimeEvents.ts#L128) — polling catch sets `connected=false` and discards error — low

401 auth expiry, CORS misconfig, DNS failure, and transient network blips all produce identical UX. Add `console.warn("[realtime] poll failed", err)` to distinguish persistent from transient.

#### [src/utils/auditLogDescriber.ts:149](src/utils/auditLogDescriber.ts#L149) — `describeChanges()` empty catch hides describer bugs — medium

Wraps entire describer logic in try/catch and falls back to raw before/after JSON. Tests at `src/tests/shared/auditLogDescriber.test.ts:820-868` explicitly lock in this swallowing behavior — so it's intentional, not an oversight. Render-safety is legitimate but doesn't require **silent** swallowing — `console.error` before fallback preserves render safety AND signals operators.

#### [src/auth.ts:26](src/auth.ts#L26) — `getRequestMeta()` bare catch returns `null` IP/UA — low

Security-relevant attribution. JSDoc mentions build-time tolerance (Next.js does throw `headers() called outside a request scope` during static generation), so a tolerant fallback is defensible — but the absence of any log call isn't. One `logger.warn` line fixes it.

### mirror-tests (8 confirmed)

Tests that re-encode the implementation rather than verify observable behavior. Two are HIGH severity because they touch security paths.

#### [src/features/persons/**tests**/AddPeople.test.tsx:45](src/features/persons/__tests__/AddPeople.test.tsx#L45) — types name+email but only asserts `expect.any(FormData)` — **HIGH**

The test types `"John Doe"` and `"john.doe@example.com"` but asserts only that `createPerson` was called with `expect.any(FormData)` — the payload is never inspected. If the form submitted empty FormData, wrong field names, or stale state, the test still passes. Same pattern at `AddTeam.test.tsx:27`, `UpdatePersonName.test.tsx:65`. **Fix:** `expect(fd.get('name')).toBe('John Doe')`.

#### [src/features/twoFactor/**tests**/SetupDialog.test.tsx:267](src/features/twoFactor/__tests__/SetupDialog.test.tsx#L267) — Escape on `document.body` instead of dialog — **HIGH**

Inline comments self-incriminate: `"MUI may or may not call the handler; in either case onClose should not fire at step 2"`. #### [src/features/twoFactor/**tests**/SetupDialog.test.tsx:171](src/features/twoFactor/__tests__/SetupDialog.test.tsx#L171) — types 2FA code but never asserts it reaches FormData — medium

Types `"123456"` into the verification input, submits the form, asserts only `confirmAction).toHaveBeenCalled()`. **No test anywhere in the codebase asserts the typed code reaches the action** — verifier confirmed via repo-wide grep. If the input lost its `name="code"`, 2FA verification would silently submit empty payloads.

#### [src/features/realtime/**tests**/ActivityFeed.test.tsx:88](src/features/realtime/__tests__/ActivityFeed.test.tsx#L88) — claims to test "different icons" but only asserts summary text — medium

Test name promises "renders create, update, and delete events with different icons" but assertions only verify the summary strings the test itself supplied (`"Created"`, `"Updated"`, `"Deleted"`). The icon `switch` (`PersonAddIcon`/`EditIcon`/`DeleteIcon`) is the actual behavior being claimed but never tested. Collapsing the switch to a single icon wouldn't fail this test.

#### [src/tests/server/auth.test.ts:210](src/tests/server/auth.test.ts#L210) — claims to test "permissions refresh" but only asserts shape — high

Asserts `permissionsVersion` was bumped and `permissions` is an object — both true even if the refresh logic silently kept stale permissions. The **immediately following test** at line 257 demonstrates the stronger pattern (`expect(result.permissions["person:create"]).toBe(true)`) — proving the assertion shape is trivially available. #### [src/features/twoFactor/**tests**/RecoveryCodesList.test.tsx:51, 59](src/features/twoFactor/__tests__/RecoveryCodesList.test.tsx#L51) — tautological tests — low

Component has no useEffect, no debounce — both tests would only fail if React itself broke. Delete both.

#### [src/features/realtime/**tests**/schemas.test.ts:67-80, 89-97](src/features/realtime/__tests__/schemas.test.ts#L67) — enum lists re-encoded and **already drifted** — low

## Verifier calibration notes

- **generic-names**: 0/4 confirmed — the "tight-scope + name-on-same-line" exception correctly disqualified all four.

## Cross-cutting observations

1. **Defensive `?? null` / `?? 0` after Zod parse** is the dominant smell in dashboard and reports queries — looks like one copy-paste template propagated across 4 report functions. **Quick win:** delete all post-parse fallbacks in `src/features/dashboard/queries.ts:153-163` and `src/features/reports/queries.ts:144-146, 246-254, 309-319, 362-370`. Leave the `relation?.field ?? null` lines alone.

2. **Job admin UI was scaffolded then abandoned** — 4 dead exports in `src/features/jobs/*` (`retryFailedJob`, `cancelJob`, `getRecentJobs`, `getJobById`) all paired with the missing detail UI. Either build the UI or delete the dead actions+queries+tests.

3. **`captureServerActionError` is unused everywhere except `global-error.tsx`** — the project has Sentry infrastructure but only one place uses it. Several client catches across 2FA, admin, jobs would benefit from explicit `captureServerActionError` calls instead of silent snackbars.

4. **Mirror tests cluster on action invocations** — multiple `expect(action).toHaveBeenCalled()` without FormData inspection across persons, teams, permissions, 2FA. Recommend a project-wide convention: when a test types specific values, the assertion must verify those values reach the action. Worth a quick lint or test-review checkpoint.

5. **Tests that re-encode enums drift silently** — the realtime/schemas test missed 6 actions and 12 entity types added since the test was written. Replace hardcoded lists with "reject unknown" contract tests.
